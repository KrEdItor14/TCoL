# Spec: Миграция сейвов для «Верхняя одежда»

## Assumptions

1. Старое имя exclusive-слота `Тело верхняя` должно безвозвратно нормализоваться в `Верхняя одежда` при любой загрузке, импорте или восстановлении сейва.
2. При конфликте, когда в сейве одновременно заполнены `Верхняя одежда` и `Тело верхняя`, предмет из уже канонического ключа остаётся экипированным, а предмет из старого ключа переносится в инвентарь. Ни один предмет не удаляется.
3. Предметы инвентаря со слотом `Тело верхняя` меняют только `slot` на `Верхняя одежда`; остальные данные сохраняются.
4. Изменение не требует нового save-envelope version: текущая миграция уже выполняется для версий 0, 1 и 2 после проверки checksum, а её результат сохраняется при следующем обычном сохранении.

## Objective

Без потери пользовательских предметов перенести все существующие сохранения с `Тело верхняя` на каноническое название `Верхняя одежда`.

Миграция работает для обычной загрузки, асинхронной загрузки из native/IndexedDB/local fallback, импорта и восстановления safety backup, поскольку все пути используют `migrateSavePayload()` и `migrateState()`.

После миграции:

- `state.equipment` содержит только канонические ключи exclusive-слотов;
- экипированный предмет из старого ключа получает `slot: 'Верхняя одежда'`;
- предметы инвентаря со старым слотом получают `slot: 'Верхняя одежда'`;
- при конфликте оба предмета сохранены, с детерминированным приоритетом канонического equipped-слота;
- `Тело верхняя` не появляется в состоянии, UI или повторно сохранённом payload.

## Tech Stack

- Vanilla JavaScript.
- Миграция: `js/save.js`.
- Канонический алиас: `data/constants.js` (`SLOT_MAP_OLD_TO_NEW`).
- Сборка runtime: `build-runtime.bat`.
- Distribution-копии: `npm run prepare:web`.
- Тесты: Node.js `assert` и `vm`, прежде всего `tests/storage-reliability.test.js`.

## Code Style

Нормализация имён слотов выполняется одним helper внутри миграции и использует алиасы из `SLOT_MAP_OLD_TO_NEW`. Логика не дублирует строки старых имён в нескольких ветках.

```js
const normalizeSlot = slot => SLOT_MAP_OLD_TO_NEW[slot] || slot;

const canonicalItem = equipment['Верхняя одежда'];
const legacyItem = equipment['Тело верхняя'];
if (canonicalItem && legacyItem) {
  inventory.push({ ...legacyItem, slot: 'Верхняя одежда', type: 'equipment', source: 'legacy' });
}
```

- Миграция изменяет входной state только после того, как определён канонический slot.
- Неизвестные legacy-слоты сохраняют существующую безопасную обработку, определённую текущей миграцией; этот модуль не меняет её семантику.
- Для конфликтов применяется явный приоритет канонического ключа, а не порядок свойств объекта.
- Перенесённый в инвентарь предмет получает уникальный `id`, `type: 'equipment'`, `qty: 1`, `source: 'legacy'` и канонический `slot`.
- `js/runtime.js`, `www/` и Android public assets не редактируются вручную.

## Testing Strategy

Расширить `tests/storage-reliability.test.js` отдельными сценариями с корректным минимальным save state:

1. **Equipped legacy item:** `equipment['Тело верхняя']` переносится в `equipment['Верхняя одежда']`, получает канонический `slot`, а старый ключ исчезает.
2. **Inventory legacy item:** equipment-предмет в `inventory` со `slot: 'Тело верхняя'` получает `slot: 'Верхняя одежда'`; его имя, описание, эффект, rarity и qty сохраняются.
3. **Conflict without data loss:** при заполненных старом и каноническом ключах канонический предмет остаётся экипированным, legacy-предмет оказывается в инвентаре и оба предмета доступны.
4. **Idempotence:** повторный вызов `migrateState()` не создаёт дубликаты и не меняет уже нормализованный результат.
5. **Envelope path:** version 2 envelope с корректным checksum успешно проходит `migrateSavePayload()` и получает тот же результат.

Запустить focused-тест миграции, слот-контракт, затем полный `npm run test:all`. После пересборки повторить migration-тест против source-кода и проверить generated runtime контрактным тестом.

## Boundaries

- **Always:** сохранять каждый предмет; нормализовать equipped- и inventory-предметы; сохранять checksum-проверку до миграции; задавать детерминированное поведение конфликта; добавлять регрессионные тесты; собирать derived-файлы генераторами.
- **Ask first:** повышение `SAVE_SCHEMA_VERSION`; изменение формата save envelope, storage-стратегии или safety-backup; изменение правил для прочих legacy-слотов; добавление зависимостей, изменение CI или Capacitor-конфигурации.
- **Never:** удалять конфликтующие предметы; принимать checksum-invalid v2 payload; редактировать generated runtime/web/Android-копии вручную; менять UI-названия, правила аксессуаров или AI-поведение; откатывать несвязанные незакоммиченные правки.

## Success Criteria

1. Любой валидный save с `Тело верхняя` в `equipment` после миграции содержит предмет в `Верхняя одежда` с каноническим `slot`.
2. Любой equipment-предмет inventory со `slot: 'Тело верхняя'` после миграции имеет `slot: 'Верхняя одежда'` и сохраняет остальные пользовательские данные.
3. Если заполнены оба ключа, `Верхняя одежда` остаётся экипированным, `Тело верхняя` переносится в инвентарь, и ни один предмет не теряется.
4. Результат миграции идемпотентен: повторная загрузка не создаёт дубликатов и не возвращает старое имя.
5. Валидные envelope v2 проходят миграцию после checksum-проверки, повреждённые продолжают отклоняться.
6. Тесты миграции и `npm run test:all` проходят; runtime, web- и Android-копии пересобраны только штатными командами.
